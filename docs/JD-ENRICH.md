# 京东订单增强

> **路线已定型（2026-09-07）**：扩展「借力打力」收割方案，已全链路上线
> （`tools/jd-ext` + 设置页导入 + 补备注自动预填）。**不走** Cookie + 命令行
> 工具路线，也不逆向 h5st —— 按单号直查需要 h5st 签名，逆向成本高且随时失效；

## 目标

账单里大量条目只有「京东」两个字，看不出买了什么。用账单里的订单号反查商品标题，自动填进备注，省掉第二步里最费神的一部分。

真实样本（2026-09-07 修正：单号是 **16 位完整京东 orderId**，早先记的 13 位是被截断的错版）：

| 账单原文 | 可提取 |
| --- | --- |
| 商品 = `京东-订单编号3590998800060006` | 京东订单号 `3590998800060006` |
| 商品 = `京东-订单编号京东-订单编号3590998800050005` | 京东订单号 `3590998800050005`（账单数据自身有重复前缀脏数据） |
| 商品 = `商户单号XP00000000000001` | 拼多多单号 `XP00000000000001` |
| 交易对方 = `京东` / `京东快递` / `京东商城平台商户` | 平台判定 |

## 侦察结论（2026-09-07，扩展抓包实测）

| 待确认点 | 结论 |
| --- | --- |
| 接口 URL | 列表 `POST api.m.jd.com/api?functionId=pcorder_center_list&appid=order-jd-com`，body `{"page":1,"s":4096,"d":1}`；搜索 `functionId=pcorder_center_search`，body `{"keyword":"...","page":1,"source":"pc_order_center"}` |
| 签名 | **order-jd-com 必须带 h5st**（v5.3，约 1100 字符，页面 JS 的 request_algo 动态生成）+ `x-api-eid-token`；`appid=details-jd-com` 的 `pcdetail_*` 系列**免签名**（但不含商品名） |
| 响应格式 | JSON。每笔订单含 `orderId / parentId / dateSubmit / itemPayInfo.totalPrice / shopInfo.shopName / wareList[{name, num, productId, imgPath}]` —— **商品名就在列表响应里**，无需单独查详情 |
| 频率限制 | 未压测（个人低频无风险）；列表一页可取 4096 条上限 |
| 规格与单价 | 列表有商品名+数量+订单实付（`itemPayInfo`），无 SKU 级规格；规格在商品详情接口（带 h5st）或详情页 HTML |

### 关键事实

- **微信账单的「订单编号」= 京东 16 位 orderId（或父单号 parentId），直接匹配可行。** 实测：账单 `3600998800010001` ↔ 列表订单完全对上；账单 `3590998800020002`（父单）↔ 列表里子单的 `parentId` 对上。
- 金额不严格相等（优惠券/京东e卡部分支付），所以**匹配以单号为准、金额仅做辅助校验**。
- 拆单合并支付：一次微信扣款对应多个子单，子单共享 `parentId`。
- 已删除的订单在列表和搜索中均不可见（进回收站）。错误格式的单号（如截断的 13 位）搜索返回「系统异常」。
- h5st 逆向成本高且京东随时更换算法 —— 走扩展「借力打力」路线可以完全绕开：页面自己发请求（签名由页面 JS 算），扩展被动收割响应。

## 侦察路线（2026-09-07 定稿：浏览器扩展）

已实测否决的两条路：

- **复制 Edge profile**：登录态丢失（打开订单页跳回 passport 登录页）。京东会话疑似设备绑定，拷贝来的 cookie 不可用。
- **CDP 调试模式 / headless**：`--remote-debugging-port` 与自动化标志会被京东风控识别（headless 直接白屏拒绝渲染；用户实测调试模式打开京东显示异常）。

- 采用：**MV3 扩展旁观收割**（`tools/jd-ext/`，小白教程见其 README），跑在用户日常浏览器里：
- 无自动化标志、无 CDP 端口，登录态就是用户自己的（扫码登录一次即成）；
- `chrome.debugger` 只启用 Network 域旁观，不注入脚本、不改页面、**不读 Cookie**；
- v1.0 起扩展只做收割 —— 早期的抓包模式、Cookie 导出/复制功能已全部删除；

兜底：扩展不可用时，仍可手动 F12 → Network 复制整条 Cookie（关键 `pt_key`/`pt_pin`）。
`pt_key` 有效期通常数天到数月，过期后需要重抓 —— 所以 UI 必须给「凭据已过期」的提示，而不是静默失败。

## 风险（动手前先想清楚）

1. **服务条款**：用非公开接口抓自己的订单，技术上可行，但不属于官方开放能力，账号有被风控的可能。只查自己的订单、控制频率，风险相对可控，但要知道这不是零风险。
2. **凭据安全**：Cookie 等同于登录态，落到本机明文存储有泄露风险。实现时应加密存储，且 UI 上要能一键清除。
3. **稳定性**：非公开接口随时可改，随时会挂。所以增强必须是**可选、可关闭、失败不影响主流程**的 —— 这一点在接口设计上已经保证：`fetchOne` 失败返回 `null`，不抛异常。

## 实现时的约束

- 默认关闭，用户在设置里主动开启才生效；
- 只在第二步「补备注」时按需触发，不做后台批量爬取；
- 每次会话限制请求数，失败重试不超过 1 次；
- 拿到的商品名只作为备注的**建议值**，用户仍可改 —— 不覆盖已写好的备注。
